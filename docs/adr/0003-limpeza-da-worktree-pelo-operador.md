# Limpeza da worktree iniciada pelo operador

Status: accepted (2026-10-22).

Julio solicitou nesta sessão uma ação para resolver o diagnóstico de árvore suja. O harness oferece **Limpar worktree** no checkout aberto: prévia dos arquivos, confirmação explícita e `git stash push --include-untracked`. A ação preserva branch, HEAD e arquivos ignorados e devolve o hash do backup com instrução de recuperação. O backup permanece no Git até ser removido pelo operador; reverter a UI não remove stashes já criados.

Esta decisão amplia a fronteira anterior do PRD e da spec, que retiraram a limpeza e seus cards do motor conversacional antigo. A nova ação é manutenção explícita do checkout registrado, fora do pipeline do pack: nunca roda automaticamente, não remove worktrees/branches e não usa reset/clean para descartar conteúdo. A entrega está em `prd-alignment#12`; a integração do setup (#03) continua bloqueada.

O supervisor coordena a exclusão entre limpeza e operações de Run, incluindo preparação, retomada, aprovação e reconciliação. Usa a identidade canônica do repositório Git para cobrir symlinks e worktrees vinculadas. A limpeza recusa Runs vivas/pausadas, conflitos, submódulos alterados e repositórios aninhados não rastreados. Prévia antiga exige nova revisão. A coordenação vale para este processo do harness; editores e outros processos externos não ficam bloqueados, e o resultado verifica novamente o estado do checkout.

A prévia inclui `git rev-parse -q --verify refs/stash` no token e lista os backups `gantry-harness-cleanup-*` já existentes. Um token antigo é recusado depois de um backup novo, mesmo que os arquivos da worktree não tenham mudado.

Quando o hash do backup é conhecido, a limpeza responde `200`. Se o `git stash push` gravou o stash e ainda assim falhou, ou se a confirmação posterior falhou, o corpo é `{ backup, clean: false, verified: false }`. O aviso diz que o estado não foi confirmado. Arquivos rastreados que continuam na worktree vão em `keep` e não devem ser apagados: removê-los e rodar `git stash apply --index` deixa o blob só no índice (`MD`, arquivo ausente no disco). Só os não rastreados vão em `remove`. A recuperação deles é `restore`: `git restore --source <hash>^3 --worktree -- <caminhos>`, que lê o commit de arquivos não rastreados do stash e não faz checkout dos rastreados. Seguir essa instrução devolve o conteúdo staged, unstaged e untracked. Os caminhos são relativos, sem caminho absoluto. O stash não é descartado. `409` fica só para o hash que não pôde ser identificado. Indisponibilidade do Git — exit 128 com `not a git repository`, ou falha de spawn `ENOENT`, `ENOTDIR` ou `EACCES` — é `503` com `code: git-unavailable` e a frase fixa de repositório inacessível, sem caminho. Identidade de autor ausente é `git-identity-unknown`, com frase fixa para definir `user.name` e `user.email`. Os demais erros de Git são `git-failed` e não dizem que o repositório está inacessível. O stderr completo fica só no log do servidor.

Quadro, workspace e registro do projeto usam um refresh de leitura separado. Enquanto há prévia/limpeza reservada, retornam as Runs persistidas sem reconciliar nem responder erro por causa da reserva. A limpeza aguarda uma reconciliação já em andamento terminar antes de escrever; novas mutações de Run continuam recusadas. O watcher acompanha apenas projetos com entrega pendente, trata a falha de cada projeto separadamente e retoma a reconciliação no ciclo seguinte. Falha real de Git na inspeção não apresenta uma árvore limpa fictícia. Indisponibilidade continua `503` com `git-unavailable`; identidade ausente e as demais falhas usam o código do caso (`git-identity-unknown`, `git-failed`) e não são relatadas como repositório inacessível. Escopos Git resolvidos são reutilizados por caminho durante a vida do supervisor; pastas sem Git não entram no cache.

Consideramos manter só a orientação de fazer commit/stash no terminal, que não resolvia a necessidade do operador na tela, e descartar alterações com reset/clean, rejeitado por perder trabalho. O stash oferece recuperação sem tornar o harness um motor paralelo de execução do Gantry.
